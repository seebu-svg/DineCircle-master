Three sibling screen modules with no shared internal sub-packages:
- `profile/profile_screen.dart` — `ProfileScreen`, a `ConsumerWidget` that composes four vertical zones (compact header, diner stats, dining preferences, grouped navigation) and hosts private helpers `_SectionHeader`, `_StatChip`, `_DiningTag`, `_MyReviewsSheet`, `_GrowthTierCard`, `_BecomeHostCard`. It navigates to other top-level screens (`BookingsScreen`, `SavedScreen`, `PaymentsScreen`, `SettingsScreen`, etc.) via a local `_push` helper.
- `user_profile/user_profile_screen.dart` — `UserProfileScreen`, a `ConsumerStatefulWidget` presenting another user's public profile (avatar, badges, stats, upcoming hosted `Dinner`s, ratings, interests, social links). It delegates safety actions (report/block/share) to `ReportSheet` and `confirmAndBlock` from `screens/safety/`.
- `preferences/preferences_screen.dart` + `food_preferences_screen.dart` — two preference editors: the first-run onboarding screen (`PreferencesScreen`) persists tastes/city through `sessionControllerProvider.updateProfile`, while the in-app editor (`FoodPreferencesScreen`) persists tastes/dietary/allergies via `sessionControllerProvider.updateSettings`.

Dependency direction is one-way outward: screens depend on `providers/session_provider.dart`, `providers/users_provider.dart`, `providers/social_provider.dart`, `models/user_profile.dart`, `models/dinner.dart`, `api/api_exception.dart`, and shared theme/widgets; they do not import each other. Server caps (8 tastes, 12 label entries) are enforced locally before calling the API to avoid 422 responses.
