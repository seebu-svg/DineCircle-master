Three sibling screen files form a linear flow plus a management hub:
- `checkout/checkout_screen.dart` implements a 3-step wizard (`_currentStep`: Seats → Guest Info → Review & Pay) driven by local state and an AnimatedSwitcher; it delegates payment to `StripePayments.confirmPayment` via a client secret from `bookingsControllerProvider.join`, then polls `waitForPaymentSettled` so the webhook is authoritative.
- `bookings/bookings_screen.dart` is the central hub (spec section 8): a `ConsumerStatefulWidget` with a `TabController` (Upcoming / Past / Payments) wrapping a `DataView<List<Booking>>`. Upcoming/Past cards are delegated to private `_UpcomingBookings` / `_PastBookings` widgets; status-gated actions live in `_UpcomingBookingCard._buildPrimaryAction` (QR ticket vs Cancel) with a `PopupMenuButton` for Directions / Contact Host / Cancel. A nested `_DirectionsSheet` renders a dark-themed GoogleMap when coordinates + API key exist, otherwise falls back to `MapScreen.openDirections` or a snackbar.
- `booking_confirmed/booking_confirmed_screen.dart` renders either a compact `_PassPreviewCard` (opens `showBookingCheckInSheet`) or a fallback pass card built from the `Dinner`; both paths show a Booking Details block and action buttons.

Dependency direction is one-way outward: screens depend on shared models (`Dinner`, `Booking`), theme tokens (`AppColors`, `AppSpacing`, `AppTextStyles`), reusable widgets (`buttons.dart`, `data_view.dart`, `booking_check_in_sheet.dart`), and Riverpod providers (`myBookingsProvider`, `bookingsControllerProvider`, `currentUserProvider`). No cross-imports between the three screen directories — navigation is the only coupling.
