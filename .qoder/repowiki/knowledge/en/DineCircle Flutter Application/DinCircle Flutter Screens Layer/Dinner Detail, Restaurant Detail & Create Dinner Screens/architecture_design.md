Three independent screen files under `lib/screens/` with no shared sub-package:
- `detail/dinner_detail_screen.dart`: a `ConsumerStatefulWidget` that watches `dinnerDetailProvider`, `reviewsForEventProvider`, `hostEventsProvider`, `isSavedProvider`, `canReviewProvider`, and `userProfileProvider` to render a hero-image SliverAppBar + scrollable detail sections (info grid, what-to-expect, menu, host card, attendees, reviews) plus a `_BookingBar` bottom bar. Host follow/save/bookmark actions go through `socialControllerProvider`; errors surface via `ApiException` caught into `SnackBar`s; navigation callbacks (`onJoin`, `onUserTap`, `onRestaurantTap`) are injected by the parent.
- `restaurant_detail/restaurant_detail_screen.dart`: a stateless `ConsumerWidget` that reads `restaurantDetailProvider` to upgrade a slim venue model to full profile + upcoming events, renders name/cuisine/rating/tags, action buttons (Directions opens `MapScreen.openDirections`, Save/Follow are stubs), an "About" section, and a horizontal list of upcoming dinners.
- `create/create_dinner_screen.dart`: a single-file six-step wizard (`_currentStep` 0–5) driven by local state (`TextEditingController`s, selected restaurant, dates, menus). Each step is a private `StatelessWidget` (`_Step1ExperienceDetails`, `_Step2Restaurant`, …) passed down as props; validation lives in `_validateStep()` keyed by field name into `_errors`. Publishing calls `eventsControllerProvider.publish(draft)` / `asDraft: true`, preview builds a local `Dinner` and navigates to `DinnerDetailScreen`. The wizard owns its own draft lifecycle (save draft, publish, edit event, pause/resume bookings, cancel event).

Dependency direction is one-way: screens depend on `providers/*`, `models/*`, `widgets/*`, and `screens/map/`; there is no cross-import between these three files except `create_dinner_screen.dart` navigating into `dinner_detail_screen.dart` for preview.
