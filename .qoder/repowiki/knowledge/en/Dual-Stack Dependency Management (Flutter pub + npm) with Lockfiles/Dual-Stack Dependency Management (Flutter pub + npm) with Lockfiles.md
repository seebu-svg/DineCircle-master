## Approach

DineCircle is a dual-stack project and manages dependencies through two independent package managers:

1. **Flutter/Dart client** — uses `pub` (the Dart package manager) with `pubspec.yaml` as the manifest and `pubspec.lock` as the deterministic lockfile.
2. **Node/TypeScript server** — uses `npm` with `package.json` as the manifest and `package-lock.json` as the deterministic lockfile.

There is no vendoring of third-party code; all packages are pulled from their default public registries (`https://pub.dev` for Dart, `https://registry.npmjs.org` for Node). No private registry configuration, `PUB_HOSTED_URL`, `GOOGLE_APPLICATION_CREDENTIALS`, `.npmrc`, or `GOPRIVATE` was found in the repository.

## Key Files

- `pubspec.yaml` — Flutter app manifest declaring direct dependencies and dev-dependencies.
- `pubspec.lock` — Generated by `pub`; pins every transitive dependency to an exact version plus sha256 checksum under `source: hosted` / `url: https://pub.dev`.
- `server/package.json` — Server manifest declaring runtime and dev dependencies.
- `server/package-lock.json` — npm v3 lockfile pinning every resolved package URL and integrity hash.
- `android/build.gradle.kts`, `ios/Runner.xcodeproj/project.pbxproj` — Native build files reference platform SDKs but do not declare additional third-party libraries beyond what Flutter's plugin system resolves.
- `.gitignore` — Excludes `build/`, `node_modules/`, `.dart_tool/`, and other generated directories so only manifests and lockfiles are committed.

## Versioning Conventions

- **Flutter dependencies** use caret ranges (`^`) in `pubspec.yaml` (e.g. `flutter_riverpod: ^2.6.1`, `dio: ^5.7.0`, `flutter_secure_storage: ^9.2.2`). The lockfile then resolves each to an exact pinned version (e.g. `flutter_riverpod: 2.6.1`, `dio: 5.11.1`).
- **Server dependencies** also use caret ranges in `package.json` (e.g. `express: ^5.2.1`, `stripe: ^23.0.1`, `zod: ^4.1.13`). The lockfile records the exact resolved version and `integrity` sha512 hash.
- The Flutter SDK itself is constrained via `environment.sdk: ^3.13.4` in `pubspec.yaml`.
- The server marks its package as `"private": true` and `"type": "module"` in `package.json`, preventing accidental publication.
- The Flutter app sets `publish_to: 'none'` in `pubspec.yaml` with a comment explaining this prevents accidental publishing to `pub.dev` for private packages.

## Upgrade Workflow

The `pubspec.yaml` comments document the intended upgrade process:
- `flutter pub upgrade --major-versions` for automatic major-version upgrades.
- Manual editing of version numbers below to the latest available on `pub.dev`.
- `flutter pub outdated` to inspect available updates.

No automated bot (Dependabot, Renovate) or CI step updating dependencies was found in `.github/workflows/server-ci.yml` (which focuses on server CI, not dependency refresh).

## Platform-Specific Dependencies

Platform integrations are declared as Flutter plugins in `pubspec.yaml` and resolved transitively into the lockfile:
- Android/iOS native bridges: `google_maps_flutter`, `flutter_secure_storage`, `flutter_stripe`, `qr_flutter`, `geolocator`, `geocoding`, `connectivity_plus`, `url_launcher`.
- These resolve further transitive packages (e.g. `flutter_plugin_android_lifecycle`, `crypto`, `dbus`) that appear only in `pubspec.lock` as `dependency: transitive`.

## Constraints and Rules

- Deterministic builds are enforced by committing both `pubspec.lock` and `server/package-lock.json`; the lockfiles record exact versions, sha256/integrity hashes, and registry URLs.
- No vendored third-party source code exists anywhere in the repo; all dependencies come from remote registries at install time.
- No custom/private package sources are configured — all packages resolve against the default `pub.dev` and `registry.npmjs.org`.
- Native build toolchains (Gradle for Android, Xcode for iOS) are managed separately via `gradlew`/`gradle-wrapper.jar` and Xcode workspace files; they are not part of the Dart/Node dependency graph.
