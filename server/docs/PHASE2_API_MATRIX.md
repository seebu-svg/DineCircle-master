## Shared contracts

- All protected REST requests use `Authorization: Bearer <opaque secret>`; JSON writes use `Content-Type: application/json`. UUID path parameters identify resources, not authority.
- Login/signup return `{token, expiresAt, user}`. Session restoration returns `{user}`. The Partner envelope reader supports these legacy roots and `{data: {...}, meta: {...}}`.
- Partner venue lists use `data.restaurants`; menu uses `data.sections`/`data.section`/`data.item`; mutations retain existing camelCase request and response fields.
- New partner list pagination uses `page`, `limit`, `total`, `hasMore`; several legacy account-wide routes have total/limit only. No pagination contract was changed.
- Customer public menu is `{restaurant, sections}` and item prices are numeric. Public queries exclude inactive sections and serialization excludes unavailable items.
- Offers is `{offers, promos, count}` from `special_menus` and `promo_codes`. `restaurant_deals` has independent status/date fields and is absent from the current customer offers model.
- HTTP errors retain `{error}` with optional Zod `issues`. Socket errors retain event `error` with `{message}`; malformed payloads now fail safely.
- Socket event names/payload keys are preserved. Messages are now trimmed, nonempty, at most 4000 characters. Receipt batches contain 1–100 UUIDs.
- QR scanner accepts a restaurant UUID, `dinecircle://menu/<uuid>` or HTTPS `/menu/<uuid>` and fetches the public menu. Branch-specific QR mapping/redirect hosting/analytics were not demonstrated.

Other route modules are discovered in `src/server.ts` but are not certified by this matrix. No full endpoint execution succeeded in this environment.
